Two fixes, independent and both worth doing. First, make the editor external-change aware: [src-tauri/src/commands/watcher.rs](src-tauri/src/commands/watcher.rs) already watches the disk; the editor should reload the buffer when the watched file changes and the buffer is clean, and merge/warn when it's dirty. Second, expose the existing tool-API to outside processes: Tauri app binds a localhost HTTP endpoint (loopback only, token-gated) that re-uses `execute_tool` from [src-tauri/src/commands/tools.rs:297](src-tauri/src/commands/tools.rs:297), and I call it via `curl` from Bash. The second handler also notifies any open editor tab so the user sees the change live. Writes only land when the app is running — when it's not, we fall back to `fs.write` (same path as today) and the editor picks it up on next launch.

Which do you want first? If the goal is purely to stop losing work, the external-change detector is smaller and self-contained. If the goal is that I edit *through* the editor so the view updates live, the HTTP surface is the one. Doing both is ideal; doing the detector first means no data loss even before the HTTP layer exists.
