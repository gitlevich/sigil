### User (18:19 UTC)

Please tell me what the lexical scope rules are currently implemented.

### Assistant (18:19 UTC)

Currently implemented priority is:

`child > sibling > ancestor/self/root > proximity > imported ontology`

Concrete behavior:

A `@Name` first looks in the current sigil’s direct children.

Then it looks at siblings in the parent scope.

Then it checks ancestors on the current path, including the current sigil itself and the root.

Then proximity runs: walk outward through enclosing subtrees, from nearest to root. At the first subtree level where exactly one matching name exists, that wins. If multiple same-name matches exist at that same level, resolution is ambiguous.

Imported ontologies are ambient outer scope. They are visible everywhere, but any local app-spec definition found by child, sibling, ancestor, or proximity shadows the imported name.

Multi-segment refs like `@A@B@C` resolve `A` by those rules, then each later segment must be a direct child of the previously resolved sigil.

Name matching is fuzzy through `sigil-core`: case-insensitive, ignores spaces/dashes/underscores, and includes simple inflections/plurals.

For renames, the frontend target selection uses these resolver rules. The backend rename cascade now scopes by target location: app-spec renames update app-spec references without sweeping `Libs`; imported ontology renames update references inside the imported ontology scope.
