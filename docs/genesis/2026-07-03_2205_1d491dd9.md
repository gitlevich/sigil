The design intent is sound — generate generously at registration, never inflect at recognition time — and for the target cases it works. But the probe surfaces one real risk and several cosmetic-noise issues.

**The one finding that matters — inflected forms can shadow an exact name.** `resolveRefName` returns the registration-order first match (`[0]`). Because `do` now registers the form `done` (irregular), an index built from affordances `["do","done"]` resolves `#done` to **`do`**, not `done` — I confirmed this directly. It's latent, not currently firing, because the property-lookup path (`findAffordance`, `findInvariantOn` at [refs.ts:253](packages/sigil-core/src/refs.ts:253) and [refs.ts:261](packages/sigil-core/src/refs.ts:261)) checks exact match *before* calling `resolveRefName`, so affordances and invariants are safe. The exposed path is sigil-name resolution in the editor ([editorScope.ts:126](src/components/Workspace/editorScope.ts:126), 132, 639), which has no exact-first guard — a sigil named `done` alongside one named `do` would misresolve. Given this is a backlog spec where `done` is a load-bearing word (the visible `!done-requires-evidence` invariant), I'd close the gap cheaply: have `resolveRefName` prefer a canonical whose own flattened base equals the query before falling back to an inflected match. That makes exact always win regardless of registration order.

**Comment contradicts code in the doubling regex.** The comment at [refs.ts:80](packages/sigil-core/src/refs.ts:80) says "final not w/x/y," but the character class `[b-df-hj-np-tv-z]` includes w, x, y, z. So `box→boxxed`, `tax→taxxed`, `fix→fixxed`, `play→playyed` all get generated. Harmless (the correct `boxed`/`boxing` come from the base branch and nobody types `boxxed`), but the guard is looser than the comment claims. To honor the comment, drop those letters from the final group: `[b-df-hj-np-tvz]`.

**Doubling over-fires on unstressed multisyllables.** English only doubles when the last syllable is stressed, which a regex can't see, so the rule invents `target→targetted`, `offer→offerred`, `water→waterred`, `render→renderred`, `open→openned`. Same story: pure noise, correct forms still present, no collision I can construct. Worth knowing it's approximate, not worth fixing.

**The `-y` branch ignores the consonant-before-y condition.** `-ies`/`-ied` should apply only after a consonant; the branch fires on any `-y`, so vowel+y words get nonsense (`play→plaied/plaies`, `enjoy→enjoied`, `stay→staied`). Net: the extension does its job and the noise is inert, but the `done→do` shadowing is a genuine latent correctness bug rooted in `resolveRefName` preferring registration order over exact match.
